Error handling in Node.js services

Most production incidents are not caused by the error itself but by what the code did next: an error that was swallowed, logged without context, or retried forever. A few habits prevent most of that.

Handle errors at the boundary

Let errors bubble up to one place per request, such as an HTTP error handler or a job runner, and decide there whether to retry, return a 4xx, or page someone. Catching errors deep in the call stack usually hides them.

Keep the error chain

try {
  await chargeCard(order);
} catch (err) {
  throw new Error(`charging order ${order.id} failed`, { cause: err });
}

Wrapping with cause keeps the original stack, so on-call engineers can reconstruct what happened.

Log in a structured format

Use structured logging so you can search by error class later. For Node, pino is fast and writes JSON by default.
